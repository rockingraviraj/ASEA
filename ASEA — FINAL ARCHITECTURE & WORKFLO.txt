ASEA — FINAL ARCHITECTURE & WORKFLOW
Autonomous Software Engineering Agent
Final System Architecture, Engineering Workflow & Implementation Direction
1. Project Definition

ASEA (Autonomous Software Engineering Agent) is an evidence-driven, policy-governed autonomous software remediation platform designed to transform software engineering tasks such as bugs, CI failures, and dependency/security issues into validated code changes and pull requests.

ASEA uses specialized AI agents, repository-level code intelligence, deterministic engineering tools, sandboxed execution, automated validation, risk assessment, and human supervision.

The goal is not to blindly replace software engineers, but to automate repetitive software engineering work while maintaining:

correctness
security
traceability
auditability
human control

The core philosophy is:

Human defines objective
        ↓
ASEA investigates
        ↓
ASEA plans
        ↓
ASEA implements
        ↓
ASEA validates
        ↓
ASEA produces evidence
        ↓
Human makes final decision
2. Core Product Positioning

ASEA should not initially position itself as another general-purpose Claude Code / Codex / Devin competitor.

General autonomous coding is already highly competitive.

ASEA's primary differentiation is:

Evidence-driven autonomous software remediation.

The system should focus initially on well-bounded engineering problems such as:

CI/CD failures
Bug remediation
Dependency/CVE remediation
Test generation and repair
Legacy maintenance

The key output is not merely:

AI-generated code

but:

Validated Code Change
+
Tests
+
Security Results
+
CI Results
+
Risk Assessment
+
Complete Evidence
+
Pull Request

This governance/evidence direction is the strongest differentiation identified during the critical industry evaluation.

     ↓

     ↓

     ↓

But this is not a rigid linear pipeline.

The actual system is a:

Failures can move execution backward:

TESTING
   ↓

   ↓

The state machine therefore behaves as a state graph, not a simple sequence.

10. PERMISSION MANAGER

Permission Manager answers:

Who is allowed to perform the action?

Example:

→ read/write source files

→ read-only

→ execute tests

Git Tool
→ branch / commit

→ create PR

Important distinction:

Policy Engine
→ Is the action allowed?

Permission Manager
→ Is this agent allowed to perform it?

Both remain separate.

41. WHY NOT KAFKA INITIALLY?

Kafka is useful at large scale, but for the initial project it adds unnecessary operational complexity.

→ Redis Streams

Enterprise Scale
→ Kafka

The critical evaluation explicitly recommends Redis Streams for MVP and Kafka later when high-throughput independent event flows justify it.

50. HARD ARCHITECTURAL RULES

These rules are non-negotiable for ASEA.

Rule 1
Agent → Agent → Agent

❌ Don't do this.

Use:

Agent → Artifact → Orchestrator → Agent
Rule 2
LLM → Shell → Host

❌ Never.

Use:

Agent → Tool → Policy → Sandbox
Rule 3

54. FINAL TECHNOLOGY-AGNOSTIC PRINCIPLE

LLM
OpenAI → Anthropic → Gemini → Local Model

without changing agents.

Similarly:

Messaging
Redis Streams → Kafka

without changing the business logic.

And:

Sandbox
Docker → gVisor → Firecracker

without changing agents.

And:

Graph
PostgreSQL → Neo4j

without changing the Context Engine contract.

This is why interfaces and clear component contracts will be extremely important when we start implementation.

56. FINAL ONE-LINE DEFINITION

ASEA is a Java-first, evidence-driven autonomous software remediation platform that transforms software issues, CI failures, and dependency/security problems into validated pull requests through policy-governed AI agents, repository-level intelligence, sandboxed execution, automated verification, failure recovery, and human-supervised delivery.
